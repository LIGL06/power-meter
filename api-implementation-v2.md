# Implementation Plan: Integrating power-meter-api into power-meter UI

## Phase 1: Infrastructure & Auth ✅ COMPLETED

## API Rework (power-meter-api) ✅ COMPLETED
Before starting Phase 2, the sibling `power-meter-api` repo was audited field-by-field against its actual running code (not just its README) to catch anything Phase 2's type-mapping table would otherwise bake in wrong. Two classes of gaps turned up — real bugs, and undocumented/inconsistent response shapes — and both were fixed, verified by the existing `npm run test:e2e` suite (extended with regression assertions for each fix) plus `npm test`/`npm run build`/`npm run lint:check`, all green:

1. **`GET /contracts?ownerId=`** silently 400'd (`forbidNonWhitelisted` rejecting an undeclared query property) instead of narrowing the admin listing — `ownerId` is now a declared, validated field on a new `ListContractsQueryDto`.
2. **Mongo duplicate-key conflicts (409s)** were missing `path`/`timestamp`, unlike every other error response — `MongoExceptionFilter` now builds the identical envelope `AllExceptionsFilter` does.
3. **CORS was wide open** (`app.enableCors()` with no origin allowlist) — now driven by a required `CORS_ORIGIN` env var (comma-separated origins; defaults to `http://localhost:5173` outside production, required with no default in production).
4. **Reading's `contract`/`billingPeriod` ref keys** are renamed to `contractId`/`billingPeriodId` on serialization (was a raw Mongoose field name leaking onto the wire).
5. **Period segment naming was inconsistent between two endpoints**: live-computed segments (`estimate.actual/projected.segments[]`) used `tariffVersionId`, persisted segments (`periods[].segments[]`) used `tariffVersion`. Persisted segments are now renamed to `tariffVersionId` too, so one `Segment` type covers both.
6. **`BillingPeriod.contract`** is renamed to `contractId` on serialization, matching the Reading rename.
7. **No formal response DTOs existed** for `GET /contracts/:id/periods*` or `GET /tariffs*` — both endpoints returned raw Mongoose documents with fields nobody had written down. Added `BillingPeriodResponseDto` and `TariffResponseDto` (Swagger/typing only — see below for why nothing was trimmed) documenting the complete real shape.

**Scope note:** the original idea for #7 was to also trim `GET /contracts/:id/periods` down to a lean list shape (dropping the per-item `tariffSnapshot` blob) and keep the full detail only on `GET .../periods/:periodId`. That was reverted after discovering the billing e2e suite asserts directly on `tariffSnapshot`, `openingImportIndex`, `closingImportIndex`, etc. from the **list** response — trimming it would have meant rewriting assertions on the most safety-critical part of the app (money calculations) for a payload-size concern that isn't blocking anything in Phase 2. Documented as-is instead; revisit only if a contract's period history actually causes a real payload problem. Similarly, `TariffResponseDto` documents `source`/`sourceUrl`/`scrapedAt`/`dacThresholdKwh` rather than hiding them — they're provenance fields, not secrets, and no endpoint currently needs them hidden.

The type-mapping table and API reference below already reflect this corrected/hardened contract, not the pre-rework one.

## Overview
The goal is to integrate the `power-meter-api` (NestJS/MongoDB backend) features into the `power-meter` React application. This involves migrating local data models to API integrations, implementing authentication, and syncing the complex billing logic.

## Analysis of source: power-meter-api
Audited directly against the running code (controllers/services/schemas), not just the README.

- **Auth** (`/auth`): JWT access (15m) + refresh (7d) pair. `register`/`login` return `{accessToken, refreshToken, expiresIn, user}`, where `user` (`UserResponseDto`) includes `role`. `refresh` takes `refreshToken` in the **body** (not a header) and rotates both tokens. `logout` revokes the stored refresh token server-side. `me` returns the same `UserResponseDto`. Roles: `ADMIN` | `USER`.
- **Contracts** (`/contracts`): a user's meter/service — **not** a 1:1 concept with "the app's user profile". A user can own multiple; a normal user only ever sees their own (`ADMIN` sees all, or one owner via `?ownerId=`, now a properly-declared/validated query field — see API Rework #1). Creating one immediately opens billing period #1. Fields on the wire: `id`, `owner` (string id), `alias`, `serviceNumber` (unique), `meterSerial?`, `address?`, `customerType`, `tariffCode` (default `'1C'`), `periodDays` (30 or 60), `billingAnchorDate`, `hasExports`, `initialImportIndex`, `initialExportIndex`, `bankedExportKwh` (server-managed), `isActive`, `createdAt`, `updatedAt`. `periodDays`/`hasExports`/alias/etc. are patchable; `serviceNumber`, `billingAnchorDate`, and both `initial*Index` fields are immutable after creation. Delete is a soft-deactivate (history retained).
- **Readings** (`/contracts/:id/readings`, `/readings/:id`): **cumulative meter indexes**, not daily deltas (matches the frontend's existing model — good news). Each reading has a real timestamp (`readAt`), not just a calendar date, and a `type: PARTIAL | COMPLETE` — posting a `COMPLETE` reading closes the current billing period and opens the next one atomically. Fields on the wire: `id`, `contractId`, `billingPeriodId` (renamed from the persisted `contract`/`billingPeriod` refs — API Rework #4), `type`, `readAt`, `importIndex`, `exportIndex`, `deltaImportKwh`, `deltaExportKwh`, `source`, `notes?`, `createdBy`, `createdAt`, `updatedAt`. The server enforces: index can only increase (422 otherwise), `readAt` can't be in the future or before the period's start, and a contract with `hasExports: false` must never send `exportIndex` (and one with `hasExports: true` must always send it). Editing/deleting is only allowed while the reading's period is still open (only `importIndex`, `exportIndex`, `notes`, `source` are patchable — `readAt`/`type` are not), and re-derives neighboring deltas automatically.
- **Billing** (`/contracts/:id/estimate`, `/contracts/:id/periods*`): all period/pricing math lives server-side. `getCurrentPeriod` lazily rolls over any period whose `expectedEndDate` has passed (closing it on its last `PARTIAL` reading, flagged `estimatedClose: true`) — there's also a nightly cron doing the same as a convenience, not a correctness requirement. `estimate` returns both the to-date actual charge and a forecast (extrapolated daily average × remaining days), each a full `BillingBreakdown` (imported/exported/net/billable kWh, energy+fixed charge, minimum-charge flag, subtotal, tax, total, and a per-segment breakdown). A period can span a season or month boundary — it's split into priced `segments`, each locked to one tariff version at close time (a `tariffSnapshot` prevents a later scrape from re-stating an already-issued bill). `GET /contracts/:id/periods*` returns the **full** period document, not a lean projection: beyond the fields the frontend needs (`id, contractId, sequence, status, startDate, expectedEndDate, actualEndDate, segments, totals`), it also carries `periodDays, openingImportIndex, openingExportIndex, closingImportIndex, closingExportIndex, openingBankedKwh, closingBankedKwh, estimatedClose, tariffSnapshot, createdAt, updatedAt`. `actualEndDate` and `totals` are always present in the JSON — `null` until the period closes, not absent. `GET /contracts/:id/periods` is **unpaginated** and includes `tariffSnapshot` (a frozen copy of every tariff version that priced the period) on every item, so a long-lived contract's period history is a non-trivial payload; fine for now, worth revisiting only if it's ever actually slow. Segment's tariff-version field is `tariffVersionId` on both `estimate.actual/projected.segments[]` and `periods[].segments[]` (unified in API Rework #5) — one `Segment` type covers both. `EstimateDto.period` is a **separate, lighter** shape (`id, sequence, status, startDate, expectedEndDate, periodDays, daysElapsed, daysRemaining`) from a `periods[]` item — don't try to reuse one `Period` type for both.
- **Tariffs** (`/tariffs`): a **global, versioned, admin-managed** catalog, not a per-user setting. Any authenticated user can `GET /tariffs` (list) and `GET /tariffs/:code?at=` (the version in force on a date); only `ADMIN` can `POST /tariffs`, `POST /tariffs/import` (bulk/scraper), or `PATCH /tariffs/:id`. A contract just references a `tariffCode`; the applicable version is resolved by date automatically. The full wire shape (documented, not trimmed — see API Rework note): `id, code, name, category, currency, effectiveFrom, effectiveTo, summerWindow, seasons[] (each with tiers[] and a subsidy), fixedCharge, minimumCharge, taxRate, dacThresholdKwh, source, sourceUrl, scrapedAt, createdAt, updatedAt`.
- **Users** (`/users`): admin-only list/create/deactivate; `GET/PATCH /users/:id` allowed for admin-or-self.
- **Errors**: uniform envelope `{statusCode, path, timestamp, message, ...}` — `message` is a **plain string** for most exceptions but a **string array** for class-validator failures (400s), and this now holds for Mongo duplicate-key 409s too (API Rework #2; previously missing `path`/`timestamp`). Any shared error-toast helper must handle both `message` shapes.
- **Misc**: global prefix `api/v1`, `GET /health` is public (liveness + Mongo connectivity) and could back a "server unreachable" banner. CORS now requires an explicit `CORS_ORIGIN` env var on the API (comma-separated origins; API Rework #3) — the frontend's dev origin (`http://localhost:5173` by default) must be in that list or every request will fail at the browser before even reaching the app. All currency figures are rounded to 2 decimals and kWh figures to 3 decimals server-side — the frontend should display these as-is, never re-round.

## Architecture decisions & mismatches (read before starting Phase 2)
The backend's data model is *not* a drop-in replacement for the local one. These are the real gaps found while auditing the API, each with a recommended resolution so Phase 2 doesn't stall on design questions mid-implementation:

1. **Missing concept: Contract.** ✅ Resolved in Phase 2 — `GET /contracts` on login; empty routes to `AddMeterPage` (`/onboarding`, `POST /contracts`); one or more holds the most-recently-created as `contract` in context. No multi-contract switcher, per plan — still an explicit non-goal.
2. **Tariffs are global and admin-owned**, but Settings' "Tariff & Tiers" tab today lets any user freely edit plan name/tiers/fixed charge/tax rate. *Resolution:* that tab becomes **read-only** for normal users (render the contract's resolved tariff from `GET /tariffs/:code`); full tariff CRUD (`POST/PATCH /tariffs`) is only ever shown to `role === 'ADMIN'`, and should live in a separate admin surface, not bolted onto the regular Settings page — defer building that admin UI until Phase 4, and only if actually needed.
3. **No server concept of a solar "export credit rate."** The API instead **banks** surplus export kWh (`Contract.bankedExportKwh`) forward to offset future imports — there's no distinct $/kWh credit. *Resolution:* drop `SolarConfig.exportCreditRatePerKwh` entirely; the Solar tab becomes just the `hasExports` toggle (`PATCH /contracts/:id`) plus a read-only display of the current banked kWh.
4. **Reading identity differs.** ✅ Resolved in Phase 3 — `readAt` is submitted as local noon converted to an ISO instant (`localNoonISOInstant()` in `domain/date-utils.ts`), preserving "one reading per day" without a time picker. **Real gap found in testing**: local noon is sometimes still in the future (e.g. logging a reading before noon), which the API rejects outright (`readAt cannot be in the future`) — fixed by clamping to the current instant whenever local noon hasn't happened yet today; the calendar date (what "already logged today" keys off) is unaffected either way.
5. **Two billing engines would drift.** ✅ Resolved in Phase 3 — `src/domain/{periods,statistics,tariff}.ts` deleted outright (confirmed via repo-wide grep that nothing outside them and the now-rewired Dashboard/ReadingEntry pages ever imported them). `domain/validation.ts`'s monotonic check stayed, exactly as planned, as a client-side fast-fail (the server is still the source of truth and re-validates).
6. **Error shape:** validation failures return `message` as a `string[]`, not a `string`. ✅ Resolved in Phase 2 (pulled forward from Phase 5, as flagged) — `getErrorMessage(error): string` in `src/lib/api.ts`, used by the new onboarding form and now also `LoginPage`/`RegisterPage`.

### Phase 2: Data Layer & Schema Alignment ✅ COMPLETED
Before starting, three parallel audits of the Phase 1 UI code (auth/state, domain/repositories, feature pages) turned up several bugs — some serious enough to undermine the new `contractReady` gate this phase adds on top of `authReady`. Fixed first, verified by `npm run build`/`npm run lint`, and by a live browser walkthrough against the real API (below):

0. **Prerequisite bug fixes** (`src/lib/api.ts`, `src/state/*`, `src/components/layout/AppShell.tsx`, `src/features/settings/SettingsPage.tsx`, `src/features/auth/*`):

   - `RegisterPage` called `toast.success`/`toast.error` with no `<Toaster/>` mounted on that route — the calls were silent no-ops. Consolidated to one themed `<Toaster/>` at the `App.tsx` root (was previously duplicated: an untheed one in `LoginPage`, a themed one only inside the authenticated `AppShell`).
   - Two independently-drifting `LogoutButton` copies (`AppShell`, `SettingsPage`) — extracted to a shared `useLogout()` hook (`src/state/useLogout.ts`).

   - Added `getErrorMessage(error): string` to `src/lib/api.ts` now (pulled forward from Phase 5, since the new onboarding form is the first real mutation needing it) and wired it into `LoginPage`/`RegisterPage`'s existing error handling too — their old `error.response?.data?.message` fallback rendered a class-validator string array via JS's bare-comma array-to-string coercion (confirmed in a live browser test: `"...a digitpassword must be..."`, no separator).
   - Not fixed (found, explicitly deferred — see Phase 4/5): `TariffTiersField`'s silent per-tier validation errors and its invalid "Add tier" default row, `solarSchema`'s always-required `exportCreditRatePerKwh`, `ReadingEntryPage`/Settings tabs' missing async-mutation error handling. 1. **Type mapping** — added new types to `src/domain/types.ts` mirroring the API DTOs (`Contract`, `CreateContractDto`/`UpdateContractDto`, `Reading`, `CreateReadingDto`/`UpdateReadingDto`, `Segment`/`TierCharge`/`PeriodTotals`, `BillingPeriodDto`, `EstimatePeriodDto`/`BillingBreakdown`/`EstimateDto`, `TariffDto` and its nested shapes, `PaginatedResponse<T>`) — **alongside**, not replacing, the legacy local types (`AppConfig`/`MeterReading`/`BillingPeriod`/`TariffConfig`/`SolarConfig`/etc.). See the scope note below for why.
2. **Repository integration** — built the four repositories exactly as originally spec'd (`contractRepository`, `readingsRepository`, `billingRepository`, `tariffRepository`), in a new `src/data/repositories/api/` directory (kept separate from the existing `src/data/repositories/*.ts` — no naming collision, no shared code to break). Verified end-to-end in a live browser run: register → land on `/onboarding` → submit → redirect to `/` → reload (no spurious logout, confirms the bug fix above) → `/onboarding` correctly redirects away once a contract exists.

### Phase 3: Core Feature Migration (Readings & Dashboard) ✅ COMPLETED
`AppDataProvider` gained a `billingReady` gate one link past `contractReady` in the same chain (`estimate`, `billingPeriods`, `refetchBilling`), fetched via `Promise.all([billingRepository.estimate(id), billingRepository.periods(id)])` once a contract is confirmed.

1. **Reading Entry** (`src/features/reading-entry`): `onSubmit` calls `readingsRepository.create`/`.update` (see the create-vs-update note below) with `readAt: localNoonISOInstant()`, `importIndex`, `exportIndex` (only when `contract.hasExports`). The existing client-side monotonic check (`isMonotonicOrEqual`) stays as a fast-fail; a slipped-through server error surfaces via `getErrorMessage`. Added the **explicit "Close this period" action** on `ProjectionSummary` (`POST /contracts/:id/periods/current/close`) behind an inline two-step confirm — not a hidden `type: COMPLETE` toggle, and not a native `window.confirm` (no dialog primitive exists in this shadcn setup yet).
   - **Create vs. update, and a bug found in testing**: the page fetches the latest 2 readings (`readingsRepository.list(contract.id, { limit: 2 })`) to detect "is there already a reading logged today," matching the old local app's UX. Editing today's reading uses `readingsRepository.update`; a fresh entry uses `.create`. **Found live**: if a period is closed early on the same day a reading was posted, that reading is still "today's" by date but now belongs to a *closed* period, which the API refuses to edit (`Cannot update a reading in a closed billing period`) — fixed by also requiring the reading's `billingPeriodId` match the currently open period before offering "update," falling through to "create" (into the new period) otherwise.
2. **Dashboard** (`src/features/dashboard`): the local `buildBillingPeriods`/`getCompletedPeriods`/`projectCurrentPeriod`/`averageConsumption`/`averageAmountPaid` are gone along with the files that defined them. "Avg. last 3 periods" is computed inline (`billingPeriods.filter(status === CLOSED).slice(0, 3)`, not worth a dedicated module for three lines); "Projected this period" reads `estimate.projected ?? estimate.actual` (falls back gracefully when `projectionAvailable` is false, e.g. no elapsed days yet). Renders the existing `Skeleton` component while `!billingReady` (pulled forward from Phase 5, since a blank-flash on load would be a regression vs. today's synchronous local data).
3. **Analytics & Charts** (`ConsumptionCostChart`): feeds from `periods[].totals.{importedKwh, total}` for `status: CLOSED` periods, reversed (API is newest-first, chart wants chronological).

**Two more bugs found in live/browser testing** (beyond the `readAt`-in-the-future one under mismatch #4):
- `formatShortDate` (`src/lib/format.ts`) assumed a bare `"YYYY-MM-DD"` and appended `T00:00:00` itself — malformed on the full ISO instants `BillingPeriodDto.startDate`/`Reading.readAt` actually are. Fixed to branch on whether the input already contains `T`.
- `formatCurrency` hardcoded `USD` — every real remaining call site is a live `MXN` amount. Now takes an optional `currency` param (API responses' own `currency` field is passed explicitly at each call site).
- Chart period labels showed one calendar day off (e.g. "Aug 24" for a period that actually started "Aug 25"): `startDate` is UTC midnight, which shifts to the previous local calendar day once `formatShortDate` reinterprets it in a negative-UTC-offset timezone. Since period boundaries are calendar dates, not moments in time (unlike `readAt`), the chart now reads the UTC date directly (`startDate.slice(0, 10)`) instead of reinterpreting it locally.

**Known, not fixed:** `npm run lint` holds at 8 errors/2 warnings (from 6 at the end of Phase 2) — the two new instances are the billing-fetch effect (`AppDataProvider`) and the latest-readings-fetch effect (`ReadingEntryPage`), both mirroring the exact same pre-existing `react-hooks/set-state-in-effect` pattern already accepted for `authReady`/`contractReady`. No new categories of lint issue.

### Phase 4: Complex Logic Translation ✅ COMPLETED
1. **Billing projection**: ✅ Done as part of Phase 3 — `projectCurrentPeriod` and its local billing engine are deleted (not reimplemented); `ProjectionSummary` now renders `EstimateDto` directly. There's only one calculation left to drift (the server's).

No edit form for normal users. 3. **Tariff management (admin-only)**: built as a separate screen at `/admin/tariffs` (route + nav item gated on `user.role === 'ADMIN'`), reachable independent of whether the admin has a personal contract (see bug list below). Lists versions for a code (`GET /tariffs?code=`), edits an existing version's tiers/charges via `PATCH /tariffs/:id`, publishes new versions via `POST /tariffs`, and bulk-imports via pasted JSON → `POST /tariffs/import`. The old tier-array editor survives here, reworked for the API's per-season `TariffTier` shape (`SeasonTiersField`), with per-field error display added (the original silent-error bug, now genuinely fixed rather than just hidden).
4. **Contract settings**: the "Solar & Export" and "Billing Period" Settings tabs now call `PATCH /contracts/:id` — `hasExports` and `periodDays` respectively. `SolarConfig`/`TariffConfig`/`billingPeriodDays` and the rest of the now-dead local config surface were deleted from `AppConfig` (only `profile` remains local); copy on both tabs states the "applies next period, not retroactively" behavior.

**Bugs found and fixed while implementing/testing Phase 4** (live browser session, see below):
- **Cross-account contract leak (serious)**: `AppDataProvider`'s bootstrap fetch called `GET /contracts` with no `ownerId`. For a normal user the API self-scopes regardless, but for an `ADMIN` it returns *every* user's contracts — `items[0]` (newest system-wide) silently became "the" admin's contract. Reproduced live: logging in as the seeded admin attached the session to a just-created regular user's meter, with full read/write access through the normal UI. Fixed by always passing `ownerId: user.id` (a no-op for non-admins, self-scoping for admins) — `contractRepository.list()`, `AppDataProvider.tsx`.
- **Admin screen unreachable without a personal contract**: `/admin/tariffs` was nested under the same route guard that redirects to `/onboarding` when `!contract`. A pure-admin account (no meter of their own — exactly the seeded admin) got stuck at onboarding and could never reach Tariff Management. Fixed by moving `admin/tariffs` to its own top-level route, gated only on `isAuthenticated` + `role === 'ADMIN'` — `App.tsx`.
- **Admin edit form silently loaded blank/stale values**: `VersionEditor`'s "Edit" button called `reset(versionToFormValues(version))` synchronously inside the click handler, in the same tick as the `setEditingId` that also flips the `code`/`effectiveFrom` `disabled` props. Top-level scalar fields (`name`, `effectiveFrom` confirmed via live DOM inspection) silently kept their blank-template values while nested `useFieldArray` tier fields updated correctly — a partial, hard-to-notice failure. Fixed by moving the reset into a `useEffect` keyed on the edit target, react-hook-form's documented pattern for resetting with data that arrives/changes after the initial render.
- **Billing state leaked across logins**: the billing-fetch effect only reset `estimate`/`billingPeriods`/`billingReady` when `contract` was `null`, not when `contractReady` itself went back to `false` on logout — so a second account logging in on the same browser session could briefly render the previous account's billing numbers. Fixed by resetting on `!contractReady` too.
- **`tariffRepository.import()` mistyped its response**: typed as `TariffDto[]`, but `POST /tariffs/import` actually returns `{inserted, skipped}` — caught by curl-verifying the exact endpoint before wiring the UI, not by TypeScript (the repository layer was simply wrong). Fixed the type and `ImportPanel`'s success toast.

## Post-Phase-5 functionality audit (API ↔ UI parity)
Full endpoint-by-endpoint and feature-by-feature review, done after Phase 5 to check nothing was missed on either side before starting the tariff scraper and further UI work. See the analysis artifact delivered alongside this update for the complete breakdown; summary of the real gaps found:

- **User profile/account management has zero real-API backing.** Settings' "Profile" tab is 100% local (`localStorage`), never touches `GET/PATCH /users/:id` or `/auth/me`. There's also no `usersRepository` at all in `src/data/repositories/api/` — the entire `/users` module (list/create/deactivate for admins, self-service view/update) has no frontend representation. Compounding this, the API itself has no password-change endpoint yet (`UpdateUserDto` excludes `password` with a comment pointing at "a dedicated flow" that doesn't exist) — so even a real Profile tab couldn't offer password changes until the API adds one.
- **No reading history view.** `readingsRepository.list()` supports pagination/date/type filters and `.remove()` already exists at the repo layer, but the only consumer (`ReadingEntryPage`) ever fetches the latest 2 readings for its "already logged today" check. There's no page listing past readings or deleting one.
- **No per-period detail/breakdown view.** `billingRepository.period(contractId, periodId)` exists at the repo layer but is never called — Dashboard's chart only shows aggregate totals per closed period, with no drill-down into the segment/tier-by-tier pricing breakdown the server already computes and stores (`tariffSnapshot`, `segments`).
- **Contract detail/deactivate unused.** `contractRepository.get(id)` and `.deactivate(id)` exist but nothing calls them — no way to view a contract's full record independent of the bootstrap flow, or to soft-delete/deactivate a meter from the UI.
- `GET /contracts/:id/periods/current` has no repo method at all — considered a non-gap: `estimate` (which already reflects the same lazy-rollover logic) and `periods` are fetched together in `fetchBilling()`, so nothing is missing functionally, just a redundant endpoint left unwired.
- Multi-contract support remains an explicit non-goal (architecture decision #1) — a user with several meters only ever sees the most recently created.
